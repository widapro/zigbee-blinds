# Надёжность команд управления жалюзи

Дата анализа: 2026-09-27. Локальный `main`, commit `82a7fa6`, remote `widapro/zigbee-blinds`.
ESP-IDF 5.5.2; lock-файл: esp-zigbee-lib 1.6.6, esp-zboss-lib 1.6.4.
Это исходный анализ до внесения изменений. Реализованное поведение и порядок обновления описаны в [command-reliability.md](command-reliability.md). Радиосбой на оборудовании не воспроизводился.
Рассматривается Zigbee2MQTT с конвертером из репозитория и автоматизация Home Assistant, которая отправляет `cover.set_cover_tilt_position` с `tilt_position: 100` группе и отдельному устройству без проверки результата. Условное имя группы в примерах — `cover.example_group`; она объединяет несколько cover-сущностей.
Для диагностики нужно установить версии прошивки и HA/Z2M, модель координатора и родительские роутеры.

## Вывод

По коду нельзя доказать, что конкретная пропущенная команда не пришла по радио. Есть и пути отказа уже после приёма команды. Нужна наблюдаемая цепочка «отправлена → принята приложением → начато движение → завершено / ошибка».

Спящее устройство не получает бесконечно хранимый запрос: родитель временно буферизует данные до опроса. Если сообщение истекло или потерялось, ожидание нескольких минут его не восстановит. Polling должен укладываться во время хранения пакета у родителя с запасом; фактические интервалы нужно измерить. [Silicon Labs: Sleepy Devices](https://docs.silabs.com/zigbee/8.2.0/zigbee-app-framework-dev-guide-sdk-7x/14-sleepy-devices).

Практический контракт надёжности: для каждой актуальной цели получить подтверждённый результат либо явную ошибку за ограниченное время. Радиодоставка при отключённом устройстве не гарантируется. Положение здесь вычисляется по STEP-импульсам: без датчика результат программы не доказывает физический угол жалюзи.

Очередь содержит 8 элементов, MOVE объединяются по последней цели. Три устройства имеют отдельные очереди: одновременная команда трём устройствам сама по себе не переполняет одну локальную очередь.

`ZB_RESPONSIVE_MODE=0`, `ED_KEEP_ALIVE=1000`, `RX_ON_WHEN_IDLE=0` и light sleep включены в [zb_network.h](https://github.com/widapro/zigbee-blinds/blob/82a7fa6/main/zb_network.h#L11). Это не deep sleep. Значение 1000 мс в исходниках не доказывает измеренную периодичность MAC Data Request в установленной прошивке. `ED_AGING_TIMEOUT=64MIN` относится к сохранению ребёнка у родителя, а не к хранению команды 64 минуты.

Окно бодрствования 20 секунд начинается после движения. Оно не защищает первую команду после долгого простоя и не меняет в коде `RX_ON_WHEN_IDLE` или polling. Отсутствие CPU sleep не следует автоматически считать непрерывным приёмом радио.

## Порядок работы

### 1. Сделать один сбой диагностируемым

Зафиксировать версию прошивки на каждом устройстве, версии Zigbee2MQTT, координатора и его firmware, канал и родителя. В рассматриваемой схеме автоматизация отправляет команду один раз без проверки результата или повторов. Для обычной группы HA команда передаётся её участникам, а состояние группы агрегируется; это видно в [реализации CoverGroup](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/group/cover.py). Поэтому гипотеза потери Zigbee multicast не является основной для описанной схемы. Проверять MQTT-отправки и подтверждения каждой дочерней сущности, а не только состояние условной `cover.example_group`. Группу в интерфейсе можно сохранить; подтверждение и retry делать для каждого устройства отдельно.

Отдельно сверить назначение `tilt_position: 100`: конвертер переводит его в ZCL 0, то есть программное «открыто». Физическое направление зависит от механизма и настроек; его нужно проверить, но оно не объясняет плавающий пропуск одной и той же команды.

Добавить диагностическую сборку с INFO для `ZB_NETWORK` и `MOTOR`, включая допустимый максимальный уровень компиляции логов: при default и maximum WARN одного runtime `esp_log_level_set()` недостаточно, чтобы вернуть вырезанные сообщения.

Для каждого задания записывать время, источник/TSN при доступности, локальный номер, цель, текущую позицию, события received/queued/started/completed/failed/superseded, глубину очереди и код причины. Добавить счётчики received/completed/failed/duplicate/queue_rejected, длительность движения и возраст последнего успешного сетевого обмена. Накопительные счётчики хранить в RAM, без NVS-записи на каждый poll.

Свести по времени логи HA/Z2M и устройства. При необходимости записать эфир: отправка unicast, запросы данных ребёнка, ответы родителя, MAC/APS ACK, ZCL-команда и отчёт. Отсутствие callback в приложении ещё не доказывает отсутствие радиопакета. Отдельно смотреть TMC/UART ошибки и изменение reboot_count/reset_reason.

USB-подключение и подробное логирование способны менять поведение сна. Основные испытания проводить и от штатной батареи, сохраняя компактную диагностику в RAM с последующим чтением.

### 2. Исправить прошивку до включения автоматических повторов

1. Ввести единое состояние accepted/pending/running для задания. Устанавливать его в Zigbee callback до передачи worker-у. Атомарно запрещать явный sleep при pending/running, калибровке и критических операциях с мотором; согласовать владение GPIO hold. При отказе постановки возвращать состояние назад. PM-lock использовать как дополнительную защиту автоматического light sleep, проверив поведение явного `esp_zb_sleep_now()` в этой версии SDK.
2. Возвращать подробный результат мотора вместо одного bool: completed, stopped, superseded, driver_error, pulse_error, timeout. Публиковать его вместе с целью и вычисленной позицией. Ошибку до первого STEP можно обрабатывать отдельной ограниченной повторной инициализацией; после неопределённого количества импульсов нельзя слепо повторять движение, считая позицию достоверной.
3. Повтор активной цели не останавливает движение; повтор уже завершённой цели только подтверждает результат. Новая цель заменяет старую. STOP отменяет только задания старше себя; новая команда после STOP должна выполняться. Добавить номер поколения задания вместо незащищённой связи очереди токенов с одной общей целью.
4. Сброс ошибок родителя делать по подтверждённому восстановлению связи. Разделить время локальных callback и сетевого успеха. Проверить recovery/rejoin по API установленной версии, обработать результат запуска и успешного восстановления, отменять устаревшие alarms. Первый backoff сейчас 60 с, максимум 15 минут; параметры выбирать по испытаниям, исключив непрерывные сканирования на батарее.
5. Публикацию результата сделать повторяемой и доступной через read. Потеря отчёта не должна требовать повторного движения. Контролировать binding в configure и не проглатывать его ошибку. Не считать `ESP_OK` от отправки отчёта свидетельством получения его HA.

При добавлении APS diagnostics изучить контракт SDK: локальный заголовок `esp_zigbee_aps.h` предупреждает, что регистрация confirm callback передаёт приложению ответственность за обработку APSDE confirm. Нельзя без проверки подменять его пустым логирующим обработчиком.

### 3. Ввести проверку результата на стороне управления

Первый полезный вариант без изменения стандартных команд: убрать оптимистичную публикацию фактического `tilt`, хранить цель отдельно, ждать свежего отчёта позиции после завершения движения, затем при отсутствии отчёта делать явный read. После проверки состояния повторять только неуспешную актуальную абсолютную цель. Старое состояние MQTT/HA или retained-пакет не служит подтверждением. Этот вариант улучшает надёжность, но слабее полной корреляции команды и ответа.

Для строгой корреляции добавить необязательную пользовательскую команду одним payload `{session, command_id, target}` и читаемый результат с теми же идентификаторами. Не писать ID и цель независимыми несогласованными атрибутами. Сохранить стандартные Window Covering команды для совместимости. Прикладной автомат: accepted → moving → completed/failed; interrupted/superseded являются отдельными результатами. Дубликат ID возвращает текущий/сохранённый результат и не перезапускает мотор. Одна 8-битная ZCL TSN не заменяет устойчивый ID задания.

На стороне Z2M/HA должен быть один владелец retry для каждого устройства и не более одной актуальной цели. Для этой установки предпочтительно реализовать контроль в слое Zigbee2MQTT, обслуживающем конвертер, чтобы он покрывал и HA-группу, и ручное управление. Если выбран HA-скрипт, он должен работать с раскрытым списком дочерних сущностей и учитывать новые ручные команды. Исходная попытка плюс, например, два повтора; исходный ориентир пауз 5 и 10 секунд с небольшим случайным разбросом. Окончательные значения подобрать с учётом реального timeout адаптера и его штатных повторов. Не запускать параллельные повторные транзакции поверх ещё незавершённого `entity.command()`.

Timeout принятия отделить от timeout движения: полный ход при максимальных motor_steps и низкой скорости может длиться значительно дольше 10 секунд. Пока устройство подтверждает движение к нужной цели, повторять саму команду не требуется. Если потерян итоговый ответ — запросить результат. После дедлайна показать ошибку пользователю. STOP и новая ручная команда отменяют старые повторы; просроченная команда не должна неожиданно выполниться после восстановления связи.

Явно определить поведение после перезапуска устройства/контроллера: новый boot/session делает старые подтверждения недействительными; сначала сверить состояние и срок актуальности цели. Не обещать exactly-once через перезагрузки без механизма хранения и восстановления. MQTT QoS не подтверждает выполнение Zigbee-команды мотором.

### 4. Проверить влияние сна отдельно от логики команд

Сравнить на одном устройстве при одинаковых моторных настройках, CPU-частотах и размещении: текущий sleepy-режим; отсутствие light sleep при прежнем RX-off; отсутствие light sleep с постоянно включённым RX. `ZB_RESPONSIVE_MODE=1` подходит для предварительной проверки, но одновременно меняет CPU-частоты и поэтому не изолирует только радио/сон. При изменении объявленных сетевых свойств проверить результат после повторного pairing тестового устройства.

Измерить polling в простое и после приёма команды. Частый опрос в активном обмене, например 100–250 мс, является кандидатом для эксперимента, а не готовой гарантией. Использовать поддерживаемый API закреплённой версии SDK; найденные `esp_zb_set/get_default_long_poll_interval()` помечены в заголовках как внутренние. Poll Control оценивать отдельно с учётом поддержки координатора. Сначала исправить подтверждения и гонки, затем менять интервалы.

Постоянно включённое радио — диагностический режим. Финальный выбор polling и длительности бодрствования делать по измеренному току и доле успешных первых попыток. Обновление SDK исследовать отдельным изменением с проверкой changelog и регрессий, не смешивая его с исправлением приложения.

### 5. Критерии приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Первое движение после 30–60 минут простоя, а также после ночи; одновременно 3 устройства | Для каждого есть completed либо явная ошибка до дедлайна; нет тихих пропусков. |
| Принудительно потеряны команда, accepted или completed | Команда восстановлена повтором либо результат получен read; повтор не вызывает дополнительного движения. |
| Повтор той же цели во время движения и после него | Движение не перезапускается. |
| A → STOP → B; A → B → C; команда во время калибровки | Исполняется определённая политикой последняя цель; старые retry не оживают. |
| Переполненная очередь, недоступный Zigbee lock, ошибка binding | Явная диагностика, отсутствие ложного completed. |
| TMC/UART отказ до движения, RMT timeout, перезапуск во время движения | Код ошибки, корректное снятие питания и признак недостоверной позиции там, где он требуется. |
| Выключение/возврат родителя, перезапуск координатора/Z2M | Восстановление без лавины retry; просроченные цели отменены. |

Автоматические тесты будущих изменений: автомат состояний и очереди в C с принудительными переключениями; конвертер с fake timers и потерянными ответами; тесты ID/session, отмены, перезапуска и инверсии 0/100. Аппаратный прогон — порядка 1000 команд на устройство с разнообразными интервалами и отдельными длинными простоями, в пределах допустимой нагрузки механизма. Считать первую успешную попытку, число повторов, задержки принятия/выполнения и ток. Нулевые отказы в конечном прогоне не являются доказательством абсолютной гарантии.
